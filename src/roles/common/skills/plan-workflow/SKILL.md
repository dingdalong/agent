## 前置条件

如果当前不在计划模式，先调用 `enter_plan_mode` 切换到计划模式，再继续执行下方工作流。

## 小任务快速通道

当用户请求**同时满足**以下全部判定标准时，可以走快速通道；任一标准不满足时，回退完整流程（阶段 1~5），并在回复中说明回退原因。

**判定标准（全部满足才准入）**：

1. 改动可隔离到 ≤2 个已知文件或资料（附带的同步更新不计入）；
2. 需求明确：无多种实现路径、无方案或设计取舍、不改变现有内容契约；
3. 无关联影响：不影响其他模块或资料，无关联内容需要同步；
4. 验收方式明确：有一条明确的完成判据可验证结果。

**快速通道流程**：

1. 跳过 `explore` 委派：你用只读工具直接核实目标文件或资料。
2. 范围确认与方案选择合并为一次 `ask_user`：同时呈现范围摘要（为什么做 / 变更范围 / 不在本期范围 / 影响面）与方案方向。
3. 跳过 `plan` 子智能体委派：你自行设计，并做三维度自查——是否复用既有资源和模式、设计是否适度无过度设计、关键设计是否经过核实而非凭印象。
4. 计划文件用精简结构（背景 / 方案 / 涉及内容 / 验收条件）：**验收条件必须保留**，且计划文件必须自包含——干净会话中不依赖原对话上下文即可独立执行。
5. `exit_plan_mode` 提交审核不变——用户审批是快速通道的兜底。

## 计划工作流

### 阶段 1：理解需求
目标：充分理解用户请求并探索现状。通过已有知识、查阅相关资料和搜索相关内容、向用户提问来建立全面理解。

1. 评估请求的明确程度。以下情况必须先用 `ask_user` 澄清再继续：
   - 存在多种根本不同的实现路径（算法选型、架构模式、设计模式等），且用户未指定偏好——列出主要选项及各自的权衡，让用户选择方向。方案间有结构性差异时，可利用 `ask_user` 选项的 `preview` 字段附上图表帮助用户对比
   - 目标、范围或关键约束不明确（如性能要求、规模量级、兼容性要求）
   - 请求涉及取舍决策（如简洁性 vs 可扩展性）且合理选择不止一种
   不需要澄清的情况：请求已足够具体、只有一种合理实现路径、或用户明确说"你来定"。
2. 探索现状。通过 `task_delegator` 委派最多 3 个 explore 子智能体**并行**探索相关资料。本阶段只使用 explore 类型子智能体（不使用 plan 子智能体）。
   - 任务隔离到已知范围时用 1 个；范围不确定、涉及多个区域时用多个
   - 多个子智能体时，为每个指定不同的搜索方向。例如：一个查现有做法，一个查相关部分，一个查约束
   - 主动搜索可复用的现有做法和资源，避免提出已有方案即可满足的新方案
   - 如果任务不涉及任何现状（纯新增、无参照），可跳过此步
3. **范围确认**：在进入方案设计前，将已澄清的需求整理为结构化范围摘要，先在回复正文中以 Markdown 输出完整范围摘要，再调用 `ask_user` 做轻确认。范围摘要包含：
   - **为什么做**：为什么做这个需求
   - **变更范围**：本次实际变更范围
   - **不在本期范围**：明确不做什么（本次不处理、后续迭代的内容）
   - **影响面**：影响的模块、依赖和风险
   `ask_user` 仅做轻确认，选项为「确认范围」「需要调整」；选「需要调整」时，按用户反馈修订范围后再次确认。用户确认范围后，才进入阶段 2 设计方案。这一步防止需求在后续阶段失控——proposal 式的范围约定也为后续 plan 子智能体提供上游约束，避免把"未来可能要做的东西"误当本期内容。

### 阶段 2：设计方案
目标：基于阶段 1 的探索结果设计行动方案。

通过 `task_delegator` 委派 plan 子智能体设计行动方案。

委派 prompt 必须包含：
- 阶段 1 的探索结果摘要：发现了哪些相关资料、现有做法和约束
- 用户的原始需求描述和已确认的约束条件
- 阶段 1 确认的范围摘要（为什么做 / 变更范围 / 不在本期范围 / 影响面），作为 plan 子智能体的上游约束
- 要求输出详细的行动方案（含影响面、执行步骤、风险和关键文件/资源列表）

如果任务复杂度高（涉及多个独立子系统或存在截然不同的实现路径），可委派多个 plan 子智能体从不同视角设计方案（如：简洁性 vs 性能 vs 可维护性），然后在阶段 3 综合评估。

### 阶段 3：审查
目标：审查阶段 2 的方案，确保与用户意图一致。

1. 读取子智能体识别的关键文件，加深理解
2. 确保方案与用户的原始请求一致
3. 评估方案质量——检查：是否复用了既有资源和模式、设计是否适度无过度设计、关键设计是否经过核实而非凭印象
4. 对方案中的决策点做分层：
   - **必须确认**：改变现状、超出原始范畴、存在多种合理取舍——汇总后用 `ask_user` 请用户定夺
   - **合理默认采纳**：符合惯例或只有一种明显合理选择——直接采纳，在回复中简要说明
5. 检查 plan 子智能体输出中的「问题」和「假设」，合并到上一步一起向用户提出。不要把未解决的问题直接写入计划

### 阶段 4：撰写计划
目标：将最终计划写入计划文件。

调用 `write_file(path, content)` 写入计划（`path` 使用计划模式指令中给出的计划文件目录，如 `.agent/plans/fix-auth-bug.md`；按计划内容命名），然后调用 `set_plan_file(file_path=<绝对路径>)` 记录当前计划文件。计划文件必须自包含：干净会话中不依赖原对话上下文即可独立执行——定位信息与验收条件齐备。`content` 正文建议包含以下章节：
- **## 背景**：为什么要做这个改动——它解决什么问题、动机和预期结果
- **## 方案**：只写推荐方案，不列所有备选；简洁到可快速浏览又足够详细可执行；引用探索中发现的可复用资源并附路径/出处
- **## 涉及内容**：需要改动的关键文件或对象。对重复模式的改动，描述模式一次并列出代表性路径，不要逐一逐行列举
- **## 验收条件**：可验证的完成判据（命令、预期输出、行为），作为执行阶段验收的核对清单。本章节必备且只在一处定义，执行阶段引用它而不重复列举

当方案涉及状态机、多组件交互、数据流等结构性变更时，在相关章节中用 Markdown 代码块内的 ASCII/Unicode 图表辅助说明（宽度 ≤60 列），仅在文字难以表达结构关系时使用。

### 阶段 5：提交审核
在写入计划文件后，调用 `exit_plan_mode(file_path=<计划文件绝对路径>)` 提交计划供用户审核（`file_path` 用 `write_file` 返回的绝对路径）。

关键规则：
- 你的每轮回复只能以 `ask_user`（澄清问题）或 `exit_plan_mode`（提交审核）结束，不能无动作停下
- 使用 `ask_user` 仅用于澄清需求或选择方案。提交审核必须用 `exit_plan_mode`，不要用文本或 `ask_user` 询问"计划可以吗"

若用户要求修改，回到阶段 1 或阶段 3 重新沟通，修改计划后再次提交。

在工作流的任何阶段，都可以随时使用 `ask_user` 向用户提问或澄清。不要对用户意图做大的假设。目标是向用户呈现经过充分研究的计划，在实施前解决所有疑点。

## 禁止行为

- 禁止不经探索直接写计划（快速通道下用只读工具直接核实目标文件或资料，即视为完成探索）。
- 禁止未与用户确认需求就直接撰写计划（快速通道下以合并的一次 `ask_user` 完成确认）。
- 禁止不写计划文件直接调用 `exit_plan_mode`（快速通道也不例外）。
- 符合「小任务快速通道」判定标准时走快速通道不算跳过阶段；不符合标准时，禁止以「任务简单」等任何理由裁剪完整流程的阶段。
- 禁止在存在多种根本不同的实现路径时，不经用户选择就直接采用其中一种。
- 禁止在匹配到合适子 agent（`explore` / `plan`）时不委派、自己下场探索或设计（快速通道内的自行核实与设计除外）。
