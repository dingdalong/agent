## 前置条件

如果当前不在计划模式，先调用 `enter_plan_mode` 切换到计划模式，再继续下方工作流。

## 计划工作流

### 阶段 1：探索代码
目标：**先**根据用户描述查看现有代码是否已有相关实现、模式或可复用内容，为后续澄清和设计提供事实依据。

1. 通过 `task_delegator` 委派最多 3 个 `explore` 子 agent **并行**探索（本阶段只用 `explore`，不用 `plan`）。
   - 任务隔离到已知文件时用 1 个；范围不确定、涉及多个区域时用多个，每个指定不同的搜索方向（如：一个查现有实现、一个查相关组件与调用方、一个查测试模式）。
   - 委派 prompt 必须给出：用户需求的关键词/目标、要确认的具体问题、期望输出（相关文件路径、现有可复用函数/工具类/模式、约束）。
   - 主动搜索可复用的函数、工具类和现有模式，避免规划出已有实现即可满足的新代码。
2. 逃生口：若用户请求过于模糊、无法确定探索方向，先用 `ask_user` 做一次最小澄清（问清目标或范围），再委派探索。
3. 逃生口：若工作区为空项目（无任何源码文件，属纯新增、无参照），可跳过 explore 委派，在回复中明确记录"工作区为空，无代码可探索"，直接进入阶段 2。

### 阶段 2：理解需求与澄清
目标：基于阶段 1 的探索发现与用户描述，通过充分对话确认需求边界并明确验收标准。本阶段的产出是一份**经用户确认**的需求理解，而非 LLM 单方面的判断。

1. 基于探索结果，识别并向用户澄清以下类型的问题（不限于此）：
   - 存在多种实现路径（算法选型、架构模式、设计取舍等）——列出主要选项及各自权衡，让用户选择方向。
   - 目标、范围或关键约束不明确（如性能要求、规模量级、兼容性要求、边界情况处理）。
   - 探索中发现的与用户描述不一致或可能冲突的现有实现。
   - 涉及取舍决策（如简洁性 vs 可扩展性、改动范围大 vs 小）且合理选择不止一种。
2. **鼓励多轮对话**：收到用户回答后，如果又产生了新问题或不确定点，继续追问——不要把所有问题堆在一次 `ask_user` 里，可以分批问、逐步深入，直到双方都清晰。多问几轮比带着猜测设计方案要好得多。
3. 明确**可验证的验收标准**（如：某测试通过、某行为达成、某接口签名变更），作为后续设计和执行的成功判据。
4. 若任务跨多个独立子系统，先与用户确认拆分边界，避免把不相关的改动混入一个计划。
5. **方案门控**：当你认为已掌握足够信息可以输出方案时，用 `ask_user` 给出 2～3 个初步方案方向（每个方案简要说明思路与权衡），让用户选择、调整或补充信息。用户看到具体方案自然会纠偏——这比抽象地问"还有补充吗"更高效。用户选定方向后，才可进入阶段 3。

### 阶段 3：设计方案
目标：基于阶段 1、2 的结论设计实现方案。

通过 `task_delegator` 委派 `plan` 子 agent 设计方案。委派 prompt 必须包含：
- 阶段 1 的探索结果摘要：发现的相关文件、现有可复用模式与约束。
- 用户的原始需求描述与阶段 2 已确认的约束、验收标准。
- 要求输出：影响面、有序实现步骤、风险、关键实现文件列表，外加 **测试策略**（务实混合：bug 修复先写复现失败的测试再修；新功能尽量测试先行；纯重构/机械改动用"测试即验证"，保证既有测试通过）与 **验收标准**。

若任务复杂度高（涉及多个独立子系统或存在截然不同的实现路径），可委派多个 `plan` 子 agent 从不同视角设计（如简洁性 vs 性能 vs 可维护性），再由你综合评估取优。

### 阶段 4：审查方案
目标：审查 `plan` 输出，确保与用户意图一致、无未决问题。

1. 读取 `plan` 子 agent 识别的关键文件，加深理解，核对方案可落地。
2. 确认方案与用户原始请求及阶段 2 的验收标准一致。
3. 检查 `plan` 输出中的「问题」和「假设」——存在未解决项时，必须通过 `ask_user` 与用户确认后再进入阶段 5。不要把未解决的问题直接写入计划。

### 阶段 5：撰写计划
目标：将最终计划写入计划文件。

调用 `write_file(path, content)` 写入计划（`path` 使用计划模式指令中给出的计划文件目录，如 `.agent/plans/fix-auth-bug.md`；按计划内容命名），然后调用 `set_plan_file(file_path=<绝对路径>)` 记录当前计划文件。`content` 为完整 Markdown 正文，建议包含以下章节（结构为推荐，非工具强制）：
- **## 背景**：为什么要做这个改动——解决什么问题、动机、预期结果。
- **## 实现方案**：只写推荐方案，不列所有备选；简洁到可快速浏览又足够详细可执行；引用探索中发现的可复用函数/工具并附文件路径。
- **## 涉及文件**：需要修改的关键文件路径。对重复模式的改动，描述模式一次并列出代表性路径，不逐文件逐行号列举。
- **## 任务分解**：拆成 bite-sized 任务，每条含「目标 / 涉及文件 / 验证方式」，关键改动可附 1-5 行伪代码或新接口签名，有依赖的标注先后。须满足：完整覆盖「涉及文件」列出的每一处改动（不遗漏、不越界）、任务间范围互斥不重叠、每条可独立验证。此章节供 execute-plan 逐条建任务，务必具体可执行。
- **## 测试策略**：按务实混合原则说明本计划各改动的测试方式（哪些先写失败测试、哪些补覆盖测试、哪些靠既有测试回归）。
- **## 验收标准**：逐条列出可验证的完成判据（命令、预期输出、行为），作为执行阶段验收的核对清单。

### 阶段 6：提交审核
在写入计划文件后，调用 `exit_plan_mode(file_path=<计划文件绝对路径>)` 提交计划供用户审核（`file_path` 用阶段 5 返回的绝对路径）。

关键规则：
- 你的每轮回复只能以 `ask_user`（澄清问题）或 `exit_plan_mode`（提交审核）结束，不能无动作停下。
- `ask_user` 仅用于澄清需求或选择方案；提交审核必须用 `exit_plan_mode`，不要用文本或 `ask_user` 询问"计划可以吗"。

若用户要求修改，回到阶段 1 或阶段 3 重新沟通，修改计划后再次提交。

在工作流任何阶段都可随时用 `ask_user` 提问。不要对用户意图做大的假设。目标是呈现一份经过充分研究、可直接落地的计划，在实施前解决所有疑点。

## 禁止行为

- 禁止不经探索直接写计划。
- 禁止未与用户确认需求就直接撰写计划。
- 禁止不写计划文件直接调用 `exit_plan_mode`。
- 禁止以「任务简单」为由跳过任何阶段。
- 禁止在存在多种根本不同的实现路径时，不经用户选择就直接采用其中一种。
- 禁止在匹配到合适子 agent（`explore` / `plan`）时不委派、自己下场探索或设计。
