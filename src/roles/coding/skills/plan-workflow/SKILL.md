不要创建执行进度任务。

## 阶段一：核实环境事实

先读取仓库规则并定位行为入口、状态权威写入者、现有接口和相关测试。能从仓库或系统发现的事实必须自行调查，不向用户提问。首次探索将独立的文件发现、内容搜索和读取合并到同一轮并行调用；已知文件直接用 `exec_command` 的 `sed -n`、`rg` 或 `git show` 读取，不额外检查文件是否存在。

只调查与目标有关的路径。每次新增工具调用必须解决一个会改变范围、目标行为或实现方案的未知事实；复用上下文中已有的成功结果，不重复列目录、搜索相同符号、读取相同区段或运行仅用于再次确认的测试。

## 阶段二：确认用户意图

能够明确陈述目标、成功标准、使用者、范围边界、约束和当前行为后，检查是否仍有无法从环境推导且会改变方案的偏好。仅在存在这种关键选择时使用 `ask_user`，一次集中提出少量互斥选项并给出推荐值。已有用户决定直接采用；普通实现选择根据仓库惯例自行确定。

## 阶段三：补齐实现决策

围绕选定方案补齐接口或 schema、数据流、状态归属、生命周期、关键边界、失败路径、测试与验收。常量措辞、逐文件行号、普通测试夹具和实现代码留到执行阶段。规划阶段不提前实现验证资产，也不为了计划看起来全面而展开无关分支。

当目标、接口、数据流、失败路径和验收均已明确，立即调用 `submit_plan(title, content)` 一次提交自包含计划；不得再做习惯性的最后一轮搜索或复查。只有新证据产生矛盾、发现会改变方案的关键缺口或用户新增要求时，才能重新调查。

计划正文按摘要、关键改动、测试和必要假设组织，按行为分组；核心状态流用图示表达。框架负责保存和审核，不另写计划文件或重读复述。用户反馈后提交完整替代版本；批准自动执行时加载 `builtin:execute-plan`。

普通只读咨询直接给出结论。本技能已通过 `load_skill` 加载，不要重复加载。不增加反思工具、评审模型、动态重复警告或强制调用次数上限。
